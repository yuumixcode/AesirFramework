## 任务 1：RAA「框架」→「架构」概念统一

### 背景

用户发现代码注释中 RAA 被称为"框架"，但 RAA 的定位是**架构**（对象间数据流转与引用的规范），非"框架"（完整工具集解决方案）。概念不一致会误导学生与用户。

### 执行

- **明确命名错误**：`RAA 框架` → `RAA 架构`（`AesirMonoBehaviour`、`AesirScriptableObject` 基类注释、CHANGELOG 历史记录）
- **指代整体**：`本框架` / `该框架` / `框架中的` / `框架必须` → `架构`（26 个 .cs 文件）
- **README 标题句**：「架构框架」→「架构」
- **保留技术实现类**：`框架级` / `框架约定` / `框架铁律` / `框架内` / `框架基础设施` 等（描述具体实现机制时"框架"仍准确，不机械替换）

### 结果

- 提交：`387d222`（9 文件，10+26 行）
- 编译零错误
- 概念与定位一致：**RAA 是架构，Context 是其中的关键上下文类**

## 任务 2：ResetStaticsAssistant「动态添加缺陷」分析

### 问题

有 AI 提出：`ResetStaticsAll()` 遍历 `ResetStaticsCallbacks` 时，若回调中动态添加新回调（`Register()`），会导致 `InvalidOperationException: Collection was modified`。

### 分析结论

| 维度 | 判定 |
|------|------|
| 说法正确性 | ✅ 技术上成立（`List<T>` 遍历时修改会抛异常） |
| 实际触发概率 | ❌ **趋近于零**（全部注册在静态构造函数中一次性完成，重置回调内不调用 `Register`） |
| 是否需要修复 | ❌ 不需要（极简原则：低概率问题用约定杜绝） |
| 用户判断 | ✅ 正确——"应该不会出现动态添加的情况" |

### 执行

- 在 `Register()` 注释中补约定：「重置回调中禁止调用 `Register()`——遍历回调列表时动态添加会导致异常。当前全部注册均在静态构造函数中完成（一次性、非动态），不触发此问题。」
- 完整分析文档：`Docs/Analysis/ResetStaticsAssistant-动态添加缺陷分析.md`

## 任务 3：CustomLifecycle 模块评估

### 背景

模块目标：替代 MonoBehaviour 原生生命周期方法（场景中 MonoBehaviour 过多时引擎逐一调用 Update/FixedUpdate/LateUpdate 会产生卡顿，Unity 官方建议自行管理生命周期）。

### 评估结论

模块**合格地达成了设计目标**（把 N 个 MonoBehaviour 的生命周期调用收敛为 1 个代理 + 字典分发），但有 2 个中等缺陷：

| 缺陷 | 严重度 | 说明 | 建议 |
|------|--------|------|------|
| `InvokeEvent` 遍历时修改列表 | 中 | 回调中 `RemoveListener` 当前事件会跳过一个回调（自注销模式触发） | 注释约定"回调中不要 RemoveListener 当前事件"（极简） |
| `EnsureSorted` 全量排序 | 中 | 每次注册后首次触发时对全部 8 个事件列表排序（即使只有 1 个有监听） | 可选：按事件标记脏（`HashSet<MonoLifecycleEvent>`） |
| `RemoveListener` 线性查找 | 轻 | O(n)，监听少时完全够用 | 不修 |
| `RegisterAuto` 硬编码 if 链 | 轻 | 新增接口要改两处 | 不修（8 个固定事件可控） |
| 非 MonoBehaviour 句柄管理靠自觉 | 轻 | 注释已写明 | 不修（极简原则有意选择） |

### 补充建议

- `OnSceneUnloaded` 事件（统一入口）：现有 `RemoveListenerWhenOnSceneUnloaded` 已覆盖，**不急需**
- `Time.timeScale` 感知暂停：业务层封装，**框架不做**

### 结果

- 完整评估文档：`Docs/Analysis/CustomLifecycle-模块评估.md`
- 总评：**合格的性能优化组件，缺陷都在"约定可杜绝"的范围内，不需要大改**
