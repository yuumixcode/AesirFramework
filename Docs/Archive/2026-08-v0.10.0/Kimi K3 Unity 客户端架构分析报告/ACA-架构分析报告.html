UNITY CLIENT ARCHITECTURE REVIEW

Aesir Architecture（ACA）架构分析报告

面向「初学者第一个框架」定位的专家评审 · 优缺点 · 理念评估 · 课程化路线 · 睿频评价

总体结论

ACA 是一套设计自洽、工程素养扎实、与定位高度匹配的教学型 MVC 框架，架构理念无明显误区。 当前最大的短板不在设计，而在示例与文档对设计意图的执行一致性。 完成 3 项 P0 修复（均为数日工作量）后，即具备在 Unity 中文课堂开课的全部条件。

一句话概括：ACA 是一个「权限矩阵 + 单向数据流」的教学型 MVC 框架—— 纯 C# 核心（Context / Model / Service / Command / Query）+ 薄 MonoBehaviour 适配层， 用能力接口组合做编译期访问控制，用 ObservableValue 做响应式数据流， 并把 Domain Reload、PlayerLoop、监听泄漏等 Unity 脏活全部收进框架内部。

02

核心优点

STRENGTHS

真实可信的极简 定位基石

45 个文件一个下午可通读——教学框架最大的失败不是功能少，而是学生不知道"里面还有什么没讲"。「设计边界」把不做的事写成契约，本身就是课程内容。

能力接口组合 = 绝佳教学载体 设计亮点

角色 = 能力的组合，权限矩阵可打印上墙；View 没有 ExecuteCommand 可用是物理约束；显式接口实现把框架管道从自动补全里隐藏——干净的 IntelliSense 就是干净的心智模型。

fail-fast 异常消息会教人 体验优势

未注册/未初始化异常包含调用者、目标、原因猜测与中文修复指引。对目标用户而言，异常消息就是隐形的课程助教。

把「忘退订」做成基础设施 最友好设计

AddListener 返回自动注销句柄，一行绑定 OnDestroy/OnDisable/SceneUnloaded（按场景分桶）。内存泄漏防护从口头纪律变成 API 形态。

纯 C# 核心，可测试性真实 差异化卖点

Engine 层不依赖 MonoBehaviour，游戏逻辑可脱离引擎跑单元测试——课程第 10 课的宣传点。

Unity 原生脏活框架自扛 工程深度

泛型类 RIOLM 被静默跳过 → ResetStaticsAssistant 中心重置；PlayerLoop 注入自动检测补插；两阶段初始化 + 逆序销毁收口时序问题。

MVC 优先、MVP 可选的渐进结构 学习曲线

MonoViewController 双角色让第一课用最少概念跑通闭环，之后再拆层——渐进式在 API 形态上兑现，而非 README 形容词。

03

主要缺点与风险

WEAKNESSES · 按对初学者伤害排序

两个示例写入口径不一致 严重 · P0

框架承诺「状态仅通过 Command 写入」，MVC 示例遵守，MVP 示例却由 Presenter 直写 Model 并手动推送刷新。初学者唯一会照抄的就是示例——两个示例给出两条路径，动摇框架核心承诺。

写入保护是约定不是结构 严重 · P1

IView 继承 ICanGetModel，View 里 this.GetModel<T>().Increase() 完全能编译通过。能力接口挡住了 ExecuteCommand，挡不住 Model 接口的公共写方法。必须显式声明为约定并在课程中正面演示后果。

README 与真实示例两张皮 中等 · P0

README 用 AesirView + 构造注入，示例用 MonoView + 无参构造。照 README 敲代码的学生会直接困惑。

最小闭环样板量仍显厚重 中等 · P0

完整 MVC 计数器约 8 文件。MonoViewController 五文件短路径已存在，但未作为「第一步」显式文档化。

Register/Get 类型参数陷阱 较轻 · P1

按实现类注册、按接口获取 → 键不匹配。异常消息可增强为「近失识别」：检测到可赋值键时提示真实意图。

双基类体系加倍文档面 较轻

AesirView / MonoView 双轨制为 Odin 可选性付出的合理代价；课程中统一只讲 Mono* 系列即可。

缺乏运行时可视性 观察项 · P2

Context 注册了什么、ObservableValue 当前值是多少均不可见。「让学生看见架构」的调试窗口是教学放大器，值得排期。

04

架构理念评估

PHILOSOPHY REVIEW
理念判定行动
(a) 核心是处理对象关系✅ 成立原样保留，作课程开场
(b) 给予可控生命周期✅ 成立补「三层生命周期」图（模块/监听/引擎）
(c) 树形依赖 · 单向调用 · 下走上事件✅ 成立补数据流向、事件决策表、「契约式树」定义
允许单例存在✅ 成立升级为「不消灭单例，消灭单例的失控」
面向初学者：简单且灵活✅ 成立显式排序：简单 > 灵活；概念须 30 秒可类比
fail-fast 哲学 / 设计边界意识⚠️ 缺失框架已在执行，理念需「追认」

「我们不消灭单例，我们消灭单例的失控。」

建议课程金句 —— 单例的真正危害是隐式初始化时序与无法隔离的测试，ACA 已分别用两阶段初始化与纯 C# Context 化解

盲区 1：只讲了调用方向，没讲数据流向

「上直接调下、下用事件通知上」是控制流；初学者更难建立的是数据流心智：数据自上而下流动，事件自下而上冒泡，同一份数据只有一个权威来源。ObservableValue 正是其实现——Model 唯一可写，View 持只读视图。补上这句，Command 的存在理由不证自明。

盲区 2：「用事件」——哪种事件？

框架实际有四种通知机制（ObservableValue / MiniEvent / C# event / UnityEvent）。对专家是自由度，对初学者是劝退题。需要决策表：每个场景有且只有一个默认答案。

盲区 3：树形依赖是约定不是结构

Context 是扁平注册表，任何角色都能 Get 任何模块——理念里的「树」在代码里是「湖」，树靠能力接口（一半）与编写约定（另一半）画出来。理念层面承认它，课程层面配层级图教具维持它。

05

改进路线

ROADMAP
P0

统一示例写入口径

MVP 示例保留经典结构（Passive View + Presenter 推送），但写入改走 ExecuteCommand。验收：Model 写方法的调用点只出现在 Command 类中。

P0

对齐 README 与真实示例

以经受编译检验的示例为准改文档；教学主线统一 Mono* 系列。验收：README 代码贴进新工程一次跑通。

P0

显式文档化最小可用路径

第一课 MonoViewController 五文件跑通闭环，第二课拆成完整八文件。验收：新人 30 分钟从空场景到可点击计数器。

P1

写入约定显式化 + 事件决策表 + 陷阱清单 + API 冻结

约定进设计边界表；决策表一锤定音；陷阱清单配近失识别异常；课程只讲冻结清单内的 API（课程发布后每次 breaking change 都是对学生的负债）。

P2

脚手架菜单 / 运行时调试窗口 / 更多示例 / Analyzer

模板生成消除文件量恐惧；调试窗口让学生「看见架构」；示例顺序：存档 → 血条 → 背包 → 场景切换。

07

睿频评价（锐评）

NO-HOLDS-BARRED REVIEW · 每条均经源码二次核查

锐评结论：框架本体 A-，示范执行 C+

引擎层功力是商业插件级别的；但示例、文档、接口设计对框架核心承诺的执行处处在拆自己的台。 框架教给学生最重要的三句话——「写入必经 Command」「View 只读」「状态单向流动」——每一句都能在 RAA 自己的示例里找到反例。 这类问题不修复就开课，等于教练一边教「开车必须系安全带」一边自己不系。

⚠️ 重大问题（一定需要修改）

1 · 示例 Model 接口暴露可写 ObservableValue，「只读视图」承诺被自己的第一个示例击穿 严重

框架在 AbstractModel 注释、README 特性、README 快速开始三处承诺「View 经 IReadOnlyObservableValue 只读订阅，不能回写」，但实际 Counter-MVC 示例接口写的是 ObservableValue<int> Count { get; }。后果：this.GetModel<T>().Count.Value = 999; —— View 一行回写 Model，Command、单向数据流、只读视图全部形同虚设。README 写的和示例做的不一样，而错的那一份恰恰是学生会照抄的。全套代码里最严重的自相矛盾。

2 · MVP「被动视图」接口继承了 IView —— 而 IView 自带 GetModel 能力 严重

ISampleMvpCounterView : IView，接口注释写着「不直接访问 Model」，但 IView = ICanGetModel + ICanGetService。「View 不访问 Model」从接口层面就不成立——MVP 的模式边界被结构性破坏，叠加 Presenter 直写 Model，MVP 示例实际沦为了「规则豁免区」。

3 · 两个示例 OnDisable 都在用 RemoveAllListeners() 严重

OnEnable 精确 AddListener(_ctrl.Increase)，OnDisable 却 RemoveAllListeners() 一刀切——会误清其他系统挂的监听。框架自己的事件系统以「精确注销」为核心卖点，示例却在教相反的模式。教法错误的代码比没有教程更危险，学生默认示例即最佳实践。

4 · MVP 示例用 Action 属性而非 event，公开 set 访问器 严重

public Action IncreaseClicked { get; set; } —— 任何外部代码可整体替换、置空、甚至 Invoke 委托链。event 关键字存在的全部意义就是限制外部只能 +=/-=。在一个教「角色与边界」的框架里，示例自己先把边界拆了。修法：接口改 event Action IncreaseClicked;。

5 · 「状态仅通过 Command 写入」在能力矩阵层面就不成立 严重

AbstractModel 说「仅通过 Command 写入」；IService 说「能读写 Model」；MVP 示例直写；View 经 GetModel 拿得到写方法——框架自己就有三个官方通道绕过 Command。单向数据流的全部教学价值建立在「入口唯一」上。二选一必须做：改叙事（Command 是表现层写入入口），或改结构（Model 读/写双接口）。

明显问题（不改不致命，改了显著更好）

6 · 框架根单例违反了自己的静态重置铁律 中

ResetStaticsAssistant 注释明言「非泛型类请在类内声明 RIOLM 重置」——MonoLifecycleProxy 等全部遵守，唯独最重要的 AesirArchitecture 根单例没有。目前靠 Unity fake-null 机制隐式救援，「碰巧正确」≠「按原则正确」。铁律若是铁律，框架自己必须先无一处例外。

7 · 初始化顺序承诺押在 Dictionary 枚举顺序上 中

「按注册顺序初始化」的语义建立在 Dictionary 枚举顺序这个无 .NET 契约保证的实现细节上（Unregister 后再 Register 会填洞变序）。修法：List 保序 + Dictionary 索引，十行代码换结构保证。

8 · 触发器组件可见性与使用语义 已撤销 · 用户裁决

原建议 HideInInspector 隐藏触发器，已被否决：可见性是教学资产，藏起来会把自动退订机制变成黑魔法。使用语义明确为「编辑器预添加为优化（订阅时 GetComponent 复用，免 AddComponent 开销），运行时动态添加为兜底」——注释按此口径说明，而非「请勿手动添加」。

9 · 三份文档三个口径 中

CODELY.md 说 Model 有 GetService 能力（实际 IModel 没有）；README 快速开始用 IReadOnlyObservableValue（对）而示例用可写类型（错）；README 用 AesirView + 构造注入而示例用 MonoView + 无参。框架教别人「契约与一致性」，自己的文档体系先不一致。

10 · Interface 是全套框架最差的命名 轻

最核心入口与 C# 关键字 interface 同词，且返回 IContext 而非 T（子类成员要强转）。一个词制造「术语混淆 + 类型困惑」两种成本。1.0 API 冻结前是最后的改名窗口期。

11 · 示例推广「属性 getter 里做服务定位」模式 轻

Model => this.GetModel<T>() 每次访问 = 字典查找 + 初始化检查。支持热替换的理由成立，但学生极易照抄进 Update。示例注释必须显式警告「禁止用于每帧路径」。

12 · [Serializable] + auto-property 序列化注释误导 轻

注释声称 Count「可在 Inspector 中序列化显示」——Unity 原生不序列化 auto-property，能显示是因为装了 Odin。无 Odin 环境照抄的学生会对着空白 Inspector 发愣。

五个重大问题全部是「改起来以小时计、不改则每节课都在被打脸」的类型——这正是开课前修复窗口存在的意义。

骨架正确、肌理扎实，差的最后一点是示例、文档、理念三者的执行一致性。

这套框架最独特的价值：它本身就示范了它要教的东西——克制、边界、契约。课程讲 ACA，其实就是 ACA 在讲它自己。
