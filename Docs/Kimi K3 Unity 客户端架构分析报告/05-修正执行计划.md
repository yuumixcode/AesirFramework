### T1.2 GenericLocator 保序 + Dispose 真逆序（锐评问题 7 + 新发现的姊妹问题）
- **背景**：`AbstractContext.Initialize()` 承诺"按注册顺序初始化"，`Dispose()` 注释承诺"逆序销毁"——但底层是 `Dictionary<Type,T>`（枚举顺序无 .NET 契约保证），且 `Dispose()` 实际是**正序**遍历，与自身注释矛盾。
- **文件**：
  1. `Runtime/Modules/Locator/GenericLocator.cs`：增加 `readonly List<Type> _insertionOrder`。`Register`：键不存在时 `_insertionOrder.Add(key)`（覆盖注册不重复添加）；`Unregister`：同步从 `_insertionOrder` 移除；`Clear`：两者同清；`GetAll()`：按 `_insertionOrder` 顺序 yield `_registry[key]`。
  2. **先读** `Runtime/Modules/Locator/IGenericLocator.cs`，同步接口注释（不新增接口成员，保序作为实现契约写入 `GetAll()` 文档）。
  3. `Runtime/Core/Engine/Context/AbstractContext.cs` `Dispose()`：改为逆序遍历（`using System.Linq;` 后 `_serviceLocator.GetAll().Reverse()`、`_modelLocator.GetAll().Reverse()`；关停路径一次分配可接受，注释中说明）。
- **验收**：编译通过；T1.5 顺序测试通过；`AbstractContext` 文档与代码行为一致。

### T1.3 触发器组件注释显形（锐评问题 8 已撤销，改为"保持可见 + 注释说明"）
- **背景（设计裁决）**：原锐评问题 8 建议 `HideInInspector` 隐藏触发器组件，**已被用户否决并撤销**。理由：①触发器在 Inspector 可见是教学资产——学生亲眼看到框架挂了组件，才有契机理解"自动退订"的实现机制，藏起来反而把机制变成黑魔法；②调试时需要能直接确认触发器是否已挂载；③与 ACA "fail-fast、行为显形"的哲学一致。正确方向是**保持可见并主动告知**，而非隐藏。
- **语义澄清（用户二次裁决）**：触发器的使用模式是「**编辑器预添加为优化，运行时动态添加为兜底**」——`RemoveListenerExtensions.GetOrAddComponent` 的语义本身就是"有则复用、无则添加"：编辑器阶段提前挂上组件后，运行时 `GetComponent` 直接命中，**跳过开销较大的 `AddComponent`**；未预添加时运行时自动挂载仅是方便性兜底。因此注释**不得**写"请勿手动添加"，应鼓励在编辑阶段确定需要自动注销时提前挂载。
- **文件**：`Runtime/Modules/Event/RemoveListenerOnDestroyTrigger.cs`、`RemoveListenerOnDisableTrigger.cs`
- **改动**：在两个类的 XML 注释中说明：
  「本组件用于在对应生命周期（OnDestroy / OnDisable）批量注销监听。两种使用方式：**推荐在编辑阶段提前挂载**（订阅时框架经 `GetComponent` 直接复用，避免运行时 `AddComponent` 开销）；未预挂载时，框架会在订阅时**运行时自动挂载**（方便性兜底）。组件带 `[DisallowMultipleComponent]`，预挂载与运行时兜底不会重复添加。」
  同步检查 `RemoveListenerExtensions.cs` 的扩展方法注释，将"该扩展方法会自动为本组件查找或添加监听句柄"之类的表述对齐为「**预挂载优化、运行时兜底**」语义。
- **验收**：注释落盘且语义为"推荐预挂载、运行时兜底"；编译通过；组件在 Inspector **保持可见**（验证未引入任何 hideFlags 改动）；冒烟验证：预挂载的 GameObject 订阅后组件数不增加（复用命中），未预挂载的自动添加（兜底生效），两者监听均正确注销。

### 2.0 渐进式示例家族结构（本阶段的总目标形态）

| 档位 | 示例目录 | 角色链 | 框架基类 | 写入 | 读取 | Model 暴露面 | 教学定位 |
|------|---------|--------|---------|------|------|-------------|---------|
| **MVC-1 快捷** | `Counter-Mvc-Quick/`（新建）| View 兼 Controller → Model | `MonoViewController<T>` | **直写** Model | 直读（GetModel）| **可写 `ObservableValue`**（外部直接改值）| 第一课：最少概念跑通闭环（~5 文件）|

| **MVP-3 严格** | `Counter-Mvp-Strict/`（新建）| Presenter → Command 写 / Query 读 | `MonoView<T>` + `IPresenter<T>` | Command | Query | **只读 `IReadOnlyObservableValue` + 写方法** | MVP 进阶：与 MVC-3 同构 |

**Model 暴露面分档（用户补充裁决）**：「**通常档（快捷/标准）Model 直接暴露可写 `ObservableValue<T>`**——外部拿到类型后直接改值（快捷档由表现层直写，标准档由 Command 在内部直写），不为每个字段都包一层写方法；**严格档才把 Model 对外收窄为只读 `IReadOnlyObservableValue<T>`，修改必须经 Model 的对外写方法。**」Model 只读化是**严格档的写法**，不是全家族铁律。

**共享写入纪律口径（全家族统一）**：「**快捷/简单档位直写 Model 合法；标准档位起，表现层写入必须经 Command（Command 内部可直接改 ObservableValue 的值）；严格档位 Model 对外只读 + 写方法；Service 可直写。**」档位是渐进选择，不是对错——项目级约定从**标准档**起步。

**新建档位的通用规则**：
- 每个新示例目录复制对应同族基准（MVC-1/MVC-3 复制修复后的 `Counter-MVC/` 改造；MVP-1/MVP-3 复制修复后的 `Counter-MVP/` 改造），**复制后立即全量改命名空间后缀与类名前缀**（如 `Quick`/`Strict`），避免类型冲突；
- 每个新示例自带**独立 Context**（`SampleMvcQuickCounterContext` 等）——不要共享 Context，避免跨示例注册冲突；
- 每个新示例自带场景（复制对应基准场景改名 + 重挂 Panel 脚本 GUID——重挂时**保留原脚本 .meta GUID 并整体替换字段引用**，或直接场景中重新拖挂组件，确保 Inspector 引用不断链）；
- **全部档位共用同一套修复规则**（T2.3 event 化、T2.4 精确退订、T2.6 getter 警告、T2.8 场景初始值同步）——复制改造时逐条核对，不要把旧反模式带进新示例；Model 暴露面按上表分档（通常档可写、严格档只读）；
- asmdef：复用现有 `Samples~` 下各示例的 asmdef 模式（先读现有 `Counter-MVC` 的 asmdef，新示例仿建，命名空间与程序集名同步）。

### T2.1 Model 接口暴露面分档修正（重大问题 1 重构；用户裁决：通常档可写、严格档只读）
- **核心澄清**：锐评问题 1 的真正病灶**不是"示例暴露了可写 ObservableValue"**（这在通常档是合法写法），而是「**框架文档承诺只读，示例却可写——口径不一致**」。修法是**文档口径对齐示例现实（分档），而非示例强行只读**。
- **通常档（MVC-1/MVC-2、MVP-1/MVP-2）Model**：**保持 `ObservableValue<int> Count { get; }` 可写暴露，不改**。仅做：
  1. 接口/实现注释明确「通常档写法：外部可直接改 `Count.Value`（快捷档由表现层直写，标准档由 Command 内部直写）；严格档收窄为只读接口，见 Counter-Mvc-Strict」；
  2. **序列化口径（锐评问题 12，用户裁决）**：注释明确「本架构的 Inspector 序列化展示以 Odin 为**加成选项**：装 Odin 可获得更好的序列化样式与更便捷的调试体验；**无 Odin 时核心架构完全正常运行**，仅 Inspector 中该类成员的展示降级为默认样式。auto-property 不能原生序列化显示，无 Odin 环境下 Inspector 中不可见属预期行为，不影响运行。」——或按执行者便利性统一改为 `[SerializeField]` 私有字段 + 公开属性转发并注明（二选一，全家族同一 Model 内风格统一，见附录 A7）。
- **严格档（MVC-3、MVP-3）Model**（T2.10/T2.11 新建时实施）：
  - 接口：`IReadOnlyObservableValue<int> Count { get; }` + 显式写方法 `Increase()/Decrease()/Reset()`；
  - 实现：`[SerializeField] ObservableValue<int> _count = new ObservableValue<int>(0);` + `public IReadOnlyObservableValue<int> Count => _count;`，写方法内部改 `_count.Value`；
  - 注释明确「严格档：View/外部只读订阅，修改必经 Model 写方法」。

### T3.7 `AbstractContext<T>.Interface` 改名 `Instance` + 返回类型改 `T`（锐评问题 10，已裁决）
- **背景与理由（2026-08-19 用户确认裁决）**：
  - **命名**：`Interface` 与 C# 关键字 `interface` 同词，制造术语混淆；且是全套框架唯一不诚实命名的核心入口。改 `Instance` 的理由：①名实相符（就是单例实例）；②与全项目其他单例（`AesirArchitecture.Instance` 等）统一；③不制造新术语，Unity 开发者零学习成本。
  - **返回类型 `IContext` → `T`**：真实使用面分析（全项目扫描）显示 `Interface` 是**框架管道接口**——学生业务代码从不直接写 `XxxContext.Interface`（写的是 `MonoView<MyContext>` 泛型绑定），唯一直接调用点是框架默认接口实现（`IContext IContextHolder.Context => AbstractContext<T>.Interface`）和框架测试。两种返回类型对比：
    | 场景 | 返回 `IContext` | 返回 `T` |
    |------|----------------|----------|
    | 管道赋值给 `IContext` 属性 | ✅ | ✅（T 向上转型，等价）|
    | 框架测试 `Context.Interface.GetModel<T>()` | ✅ | ✅ |
    | 少数派：Context 子类自定义成员（如 `GameContext.SaveAll()`）| ❌ 需 `((GameContext)Interface).SaveAll()` 强转，新手地雷 | ✅ 直接用 |
  - **结论**：返回 `T` 严格更优——管道场景零变化，少数派场景免费消除强转（协变友好：返回类型给最具体的，用的时候自然收窄）。用户"两者区别不大"的直觉在 90% 场景成立，正因为区别不大，才更应选在边角场景不挖坑的方案。
- **改动点（全项目共 ~20 处引用，执行时全局搜索 `.Interface` 复核）**：
  1. `Runtime/Core/Engine/Context/AbstractContext.cs`：`public static IContext Interface` → `public static T Instance`（getter 内部实现不变，返回类型 `IContext` → `T`）；XML 注释**删除**「可通过 `((T)Interface)` 访问子类特有成员」一句（改名后该句失效，其消失本身就是收益证明）；注释补充「原名 `Interface`，0.9.x 起更名 `Instance` 并返回具体类型 `T`」。
  2. 框架内 6 个默认接口实现点：`IController<T>`、`IPresenter<T>`（`Runtime/Core/Engine/Modules/Interfaces/`）、`MonoView<T>`、`AesirView<T>`、`MonoViewController<T>`、`AesirViewController<T>`（`Runtime/Core/Component/`）——`AbstractContext<T>.Interface` → `AbstractContext<T>.Instance`（机械替换）。
  3. `Assets/Runestone/AesirModules/Runtime/UI/AesirBasePanelView.cs`：1 处机械替换 + 注释中「`AbstractContext{T}.Interface` 返回其 `IContext` 接口形式」的表述同步修正。
  4. `Tests/Editor/AbstractContextInitializationTests.cs`：8 处机械替换。
  5. `Assets/Runestone/AesirArchitecture/CHANGELOG.md`：记录为 **breaking change**，附迁移说明「全局替换 `.Interface` → `.Instance`；返回类型从 `IContext` 变为具体 Context 类型，此前依赖 `((T)Interface)` 强转的代码可直接去掉强转」。

## 阶段 5 · 架构调试窗口（Context Debugger）

> 目标：让学生「看见架构」——运行时可浏览全部 Context / Model / Service，并直接编辑 ObservableValue 与可序列化字段。
> 方案决策（2026-08-19 用户裁决）：**三版并行试做（IMGUI / Odin / UI Toolkit），用户亲验后三选一**。
> 功能目标（三版一致）：**(a) 便于观察**（唯一核心目标）；**(b) 可编辑部分架构实例内部的序列化字段**；**(c) 样式必须好看（重要硬指标）**。
> ⚠️ 定位（G9②）：调试窗口是**体验优化品**，不是必需品——因此 V2 Odin 方案合法存在，不以"无 Odin 可用"为前提；但核心架构闭环（G9①）不受影响，调试器消失后架构照常运行。

### 5.0 三版方案对比预览

| 维度 | V1 · IMGUI | V2 · Odin | V3 · UI Toolkit（纯代码） |
|------|-----------|-----------|--------------------------|
| 技术栈 | `EditorWindow` + `EditorGUILayout` 反射 | `OdinEditorWindow` + `PropertyTree` | `EditorWindow` + `VisualElement` + USS（纯代码，不用 UIBuilder）|
| 样式上限 | 朴素（可做基础美化：折叠组/徽标/分隔线）| 最高（Inspector 富样式开箱即用）| 高（USS 完全可控，可做到现代编辑器风格）|
| 性能 | 即时模式，频繁重绘有 GC 压力（折叠 + 手动刷新可控）| 同 IMGUI | 保留模式最优（ retained UI，仅变更重绘）|
| 无 Odin 可用 | ✅ | ❌（`#if ODIN_INSPECTOR`）| ✅ |
| 维护成本 | 低 | 极低（序列化协议自动处理）| 中（样式需手写 USS，但纯代码可 diff/AI 可维护）|
| 教学价值 | 反射编辑的直白示范 | Odin 工作流示范 | 现代 Unity 编辑器开发示范（推荐方向）|
| G10 契合 | 中 | 高（但依赖面板生态）| **高**（纯代码、AI 可读写可 diff）|

### T5.0 共享数据访问层（三版复用，只做一次）
- **文件**：新建 `Editor/Unity/Debugger/ContextRegistryScanner.cs` + `Editor/Unity/Debugger/ModuleFieldReader.cs`（核心 Editor 程序集，无 Odin 依赖）。
- **实现**：
  - `ContextRegistryScanner`：`AppDomain` 扫描所有非抽象 `AbstractContext<>` 子类 → 反射读静态 `_instance`（`BindingFlags.NonPublic | BindingFlags.Static`）→ 返回「Context 类型 + 实例（可 null）」；提供「初始化」按钮语义（不自动触发 `Instance` getter，避免编辑期意外建上下文）；
  - `ModuleFieldReader`：给定模块实例 → 经 `GetAllModels()`/`GetAllServices()` 已由上层调用 → 反射遍历可序列化字段（`[SerializeField]` + public），应用 **G10 精简**：默认只暴露 `ObservableValue<T>` 与 `[SerializeField]` 字段，内部实现字段（`_valueChangedEvent`、缓存等）过滤；`ObservableValue<T>` 特判——经 `PrivateValueFieldName` 常量读 `value`、写回经 `Value` setter 或 `InvokeMethodName` 触发通知（复用常量，不硬编码字符串）。
- **验收**：被三版窗口共同引用；EditMode 扫描到全部 6 个示例 Context；`ObservableValue` 读写经通知链（改值后订阅者收到回调）。

### T5.6 Inspector 精简原则写入架构文档（G10 理念固化）
- **背景（用户核心理念，2026-08-19）**：使用 Odin 优化 Inspector 的核心目标是**优化调试过程**，而非承载配置。两条子原则：①配置足够精简——AI 时代，不需要展示给开发者的细小内容就不上面板；②不彻底依赖面板配置——面板点击操作对 AI 难驱动、易出错、不可 diff，是 AI 辅助开发的速度瓶颈。因此 Inspector 是**加成**，非必要时不把配置放在面板上。
- **文件**：
  1. `README.md` 设计原则节新增第 7 条：「**Inspector 精简原则（AI 优先）**——Odin 优化的目标是调试可见性；核心配置首选代码与资产文件（AI 可读写、可版本管理），Inspector 仅作调试加成；非必要、非重要内容不进面板」；
  2. 阶段 3 新建的《常见陷阱清单.md》补一条：「不要把核心配置只放在 Inspector 面板上（代码不可配）——AI 无法驱动面板操作，且配置无法 diff/搜索」；

### T5.7 Odin 定位三条铁律写入架构文档（G9 理念固化）
- **背景（用户核心理念，2026-08-19 强化）**：Odin 在 ACA 中的定位需从"加成选项"（原 G9 一句话）升级为明确的三层心智模型，让开发者与学生一眼看清"哪里能用 Odin、哪里不能"。
- **三条铁律**：
  1. **核心架构流程闭环不依赖 Odin**——Context 注册、Model/Service 初始化、Command/Query 执行、ObservableValue 通知，全链路无 Odin 可运行；
  2. **架构调试器是优化品**——调试窗口优化开发体验，可以使用 Odin（V2 方案合法），不需要为"无 Odin"牺牲调试体验；
  3. **样式优化与代码逻辑分离**——以 `ObservableValue` 为范例：逻辑（值比较 + 通知）无 Odin 照常运行，样式（Inspector 内联 + OnValueChanged）由 Odin AttributeProcessor 增强。
- **文件**：
  1. `README.md` 设计原则节新增第 8 条：「**Odin 三条铁律**——核心闭环不依赖 Odin / 调试器等体验优化品可用 Odin / 样式优化与代码逻辑分离（ObservableValue 为范例）」；
  2. `README.md` 依赖说明或安装节补一句：「Odin Inspector 为可选增强（样式与调试体验），非运行前置——核心架构无 Odin 可完整运行」；
  3. `CODELY.md` 手动项（T3.5 合并提交给用户）：包依赖/开发规范节补同口径，明确三个包的 Odin 定位（Architecture 独立无依赖、Modules 无依赖、Inspector 强依赖）。
- **验收**：README 中三条铁律逐字落盘且与 G9/G10 表述无矛盾；检查 README 全文不再有"Odin 可选"与"Odin 必需"的冲突表述；`ObservableValue` 作为铁律 3 的范例被明确引用。

**阶段 5 出口标准**：三版窗口全部编译通过（V1/V3 无 Odin 可编译，V2 有 Odin 可编译）+ 各自功能验收（T5.1–T5.3）通过 + T5.4 对比文档产出 + **用户三选一后落选版本删除、保留版菜单归一** + T5.5 文档落盘 + T5.6 落盘；git 提交一次（如「新增 Context Debugger 三版试做（IMGUI/Odin/UI Toolkit），实测对比后选定 X 版；设计原则补 Inspector 精简原则（AI 优先）」）。
