# 02 · 架构理念评估

> 评估对象：作者提出的架构理念——
> **(a)** 架构的核心是处理不同物体对象之间的关系；
> **(b)** 给予不同物体对象可控的生命周期；
> **(c)** 保持树形依赖、单向调用（上→下直接调用，下→上走事件），角色分层（MVC / MVP / MVC-S）；
> 以及两条原则：**面向初学者必须简单且灵活**、**允许单例存在**。

---

## 一、总体结论

**这套理念没有明显误区，方向是正确的，而且 ACA 的代码已经在忠实地执行它。**

但它目前是一份"经验直觉的集合"，还不是一套"可教学的公理体系"。距离课程化，缺的不是正确性，而是**三条没有被你说出来的隐式规则**——你已经把它们写进了框架代码里，却没有写进理念里。课程化的过程，本质上就是把这些隐式规则显式化的过程。

---

## 二、逐条评估

### (a) "架构的核心是处理对象之间的关系" —— ✅ 成立，且是最高优先级

这个判断抓住了架构与"代码技巧"的分水岭。初学者写 MonoBehaviour 的痛苦几乎全部来自关系失控：`Find` 满天飞、互相 `GetComponent`、静态字段乱传。

ACA 把这个理念落实成了两样具体的东西：

1. **Context 注册表** —— 所有"谁认识谁"收口到 `Configure()` 一个方法里，关系从散落在 N 个文件里的隐式引用，变成一处可审阅的显式声明；
2. **能力矩阵** —— "谁被允许对谁做什么"从口头约定变成编译期约束。

**评估：理念正确，且执行到位。** 建议在课程第一课就把它作为开场："架构不管你的代码写得好不好，只管你的对象之间乱不乱。"

### (b) "给予对象可控的生命周期" —— ✅ 成立，且 ACA 做得比理念表述的更深

ACA 在生命周期上实际做了三层：

| 层 | 机制 | 解决的问题 |
|----|------|-----------|
| 模块生命周期 | 两阶段初始化（注册→按序 Initialize）+ 逆序 Dispose | 模块间依赖时序 |
| 监听生命周期 | `AutoRemoveListenerHandle` + 生命周期触发器 | 内存泄漏（初学者第一大坑） |
| 引擎生命周期 | PlayerLoop 注入、Domain Reload 静态重置 | Unity 特有的时序暗坑 |

**评估：理念正确。值得注意的是，你对"可控"的理解已经超过了多数同类框架作者**——多数人只想到第一层。课程中建议把这三层画成一张图讲，这是 ACA 区别于"玩具框架"的硬核证据。

### (c) "树形依赖、单向调用、下走上事件" —— ✅ 成立，但这是最需要补强的部分

这是经典分层架构的正确表述，ACA 的数据流也确实是这么走的：

```
View ──输入──▶ Controller ──▶ Command ──写──▶ Model
View ◀──订阅── ObservableValue ◀──通知──┘
```

## 三、理念盲区

### 盲区 1：你只讲了"调用方向"，没讲"数据流向"

"上层直接调用下层，下层通过事件通知上层"描述的是**控制流**。但对初学者来说，更难建立的心智模型是**数据流**：

> **数据自上而下流动，事件自下而上冒泡；同一份数据只有一个权威来源（Single Source of Truth）。**

你的 ObservableValue 恰恰就是单向数据流的实现——Model 是唯一可写者，View 只持有 `IReadOnlyObservableValue` 只读视图。这是 ACA 最优雅的设计之一，但它目前在你的理念表述里是缺席的。

**建议**：在理念 (c) 中补一句——"**状态的所有权永远在下层，上层只持有只读视图；改变状态的唯一方式是向下发命令。**"有了这句，Command 模式的存在理由就不用再向学生解释了：它是"单向数据流"的自然推论。

### 盲区 2："下层用上事件"——哪种事件？初学者会在这里选择瘫痪

ACA 里实际存在四种"通知"机制：`ObservableValue<T>`、`MiniEvent`、原生 C# `event`（MVP 示例在用）、以及 Unity 世界的 `UnityEvent`/Button.onClick。理念说了"用事件"，但没有说**什么场景用哪个**。

对专家这是自由度，对初学者这是第一道劝退题。需要一个一锤定音的决策表：

| 场景 | 唯一推荐 |
|------|---------|
| Model 里的状态变了要通知外界 | `ObservableValue<T>` |
| 一次性/瞬时通知（"门开了""怪死了"），无状态 | `MiniEvent` / `MiniEvent<T>` |
| View 把自己的输入暴露给 Presenter（MVP 内部） | 原生 C# `event` |
| Inspector 里拖拽连线的 UI 交互 | `UnityEvent` |

**规则：每个场景有且只有一个默认答案，其余答案课程里不教。** 决策表比自由度更适合第一门课。

### 盲区 3：树形依赖是"约定"不是"结构"，需要教学手段维持

一个必须诚实面对的事实：ACA 的 Context 是一个**扁平注册表**，任何持有 Context 的角色都能 `GetModel` 到任何 Model。树形关系目前靠三样东西维持：能力接口（挡 Command）、接口设计（挡不写代码的人）、文档约定（挡所有人）。

也就是说——**你理念里的"树"，在代码里是一片"湖"，树是靠规则画出来的。** 这不是缺陷（所有同量级框架包括 QFramework 都这样），但理念层面要承认它，否则课程里学生会问"我直接在 View 里调 Model 的方法也能跑，为什么不行"。

**建议**：理念 (c) 补充定义——"树形依赖在本框架中是**契约式**的：由能力接口强制执行一半，由编写约定守护另一半"。然后配一张"层级图"作为课程的核心教具，反复使用。

## 四、对两条原则的评估

### "允许单例" —— ✅ 完全正确，且论证方式可以再升级

你的论证（IOC 容器本身也是全局单例）是对的。面向初学者，还可以把这个问题讲得更本质：

> 单例的真正危害从来不是"全局可访问"，而是两样东西：**隐式的初始化时序**和**无法隔离的测试**。

而 ACA 恰好把这两个危害都处理了——两阶段初始化让时序显式化；纯 C# Context 让测试可以 `new` 出独立实例。所以更准确的表述应该是：

> **"我们不消灭单例，我们消灭单例的失控。"**

这句话建议直接作为课程金句。它把"允许单例"从一种妥协，升级成一种有方法论支撑的主动选择。

### "面向初学者：足够简单、足够灵活" —— ✅ 正确，但两个词要排主次

"简单"和"灵活"在框架设计里经常是互相拉扯的。从你的框架实际决策（极简边界、fail-fast、不做池化）来看，你真实的优先级是**简单 > 灵活**——这是对的。建议在理念中显式排序：

> **当简单与灵活冲突时，选简单；灵活性以"不挡路"的形式保留（可替换 Loader、可选 MVP），而不是以"更多开关"的形式提供。**

另外，面向"刚做完一个 demo 的初学者"还有一个隐含要求值得写进理念：**框架的每一个概念都必须能在 30 秒内用 Unity 里已有的东西类比解释**。Context ≈ "一个全局但受控的注册表"；Command ≈ "把一次操作封装成一个类"；ObservableValue ≈ "会自动通知的变量"。ACA 的概念全部通过这个测试——这是它适合当第一框架的深层原因。

---

## 五、理念里没有、但框架已经在做的两件事

课程化时需要"理念追认"：

1. **错误处理哲学：fail-fast**。框架已经在这么做（未注册抛异常、不回滚、异常消息带修复指引）。理念里应有第六条："**框架宁可第一时间报错，也不替错误兜底**——因为兜底会把编程错误拖成运行时灵异事件，而初学者最怕灵异事件。"

2. **边界意识：架构不做什么**。README 的"设计边界"一节是 ACA 最有气质的部分，但它目前只是文档，没有上升为理念。建议理念 (a) 补一句："**处理对象关系的方式，一半是建立规则，另一半是明确不建立什么规则。**"

## 六、评估总结

| 理念 | 判定 | 行动 |
|------|------|------|
| (a) 核心是对象关系 | ✅ 成立 | 原样保留，作为课程开场 |
| (b) 可控生命周期 | ✅ 成立 | 补一张"三层生命周期"图 |
| (c) 树形单向依赖 | ✅ 成立 | 补数据流向、事件决策表、"契约式树"定义 |
| 允许单例 | ✅ 成立 | 升级为"不消灭单例，消灭单例的失控" |
| 简单且灵活 | ✅ 成立 | 显式排序：简单 > 灵活；概念可类比性测试 |
| —（缺失） | ⚠️ | 追认 fail-fast 哲学与设计边界意识 |

**最终判断：这套理念作为开源项目 + 课程的思想内核是合格的。它的风险不在"错"，而在"没说完"——而没说出来的部分恰好全都已经写在 ACA 的代码里了。你要做的不是改理念，而是把代码里已经证明正确的判断，翻译回理念里。**
